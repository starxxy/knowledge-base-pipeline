# 把「刷到的视频」变成能搜索的知识库：一份可直接抄的可行性方案

> 一条链接进去，一条能搜索、能问 AI 的笔记出来。文末附：这套流程怎么接到 AutoClaw 上。

## 一、起点：收藏夹吃灰

我刷到有用的教程就收藏，真正要用的时候却找不到。

点赞和收藏只是「标记」——它不帮我记住内容，也不让我搜索里面的信息。真正有用的是**文字和结论**，而不是那个躺在收藏夹里的视频。

于是我想做一件事：**把「我发一条链接」变成「知识库里多一条可检索的笔记」**。

先说结论：**这条路完全走得通，而且不需要服务器、不需要付费服务**。下面是可以直接抄的方案。

## 二、方案总览

```
你发一条链接
     │
     ├─ 抖音 ──► 浏览器取无水印直链 ──► 下载/合并 ──► GPU 转写 ──┐
     │                                                          │
     └─ 公众号 ──► 抓正文 + 存图 ───────────────────────────────┤
                                                                ▼
                                            AI 提炼：一句话总结 / 要点 / 金句 / 标签
                                                                │
                                                                ▼
                                       Markdown 条目 + INDEX.md + 本地浏览页
```

几个刻意的选择：

- **Markdown 优先**：文件即数据，不锁定任何软件。
- **重的东西不进知识库**：视频留在 NAS，知识库只存文字和图片。
- **没有常驻服务**：脚本跑完就退出，坏了也好修。

## 三、三个关键环节（含实现细节）

### 1. 抖音取流：别猜 CDN，用真实浏览器

抖音 Web 端是分轨的：视频一路、音频一路，播放器用 blob 地址播，页面 HTML 里拿不到能下载的链接。

做法是：用浏览器自动化打开视频页、触发静音播放，然后**从网络日志里捞出媒体直链**，逐个下载后用 `ffprobe` 识别是合流还是分轨，是分轨就用 ffmpeg 合并。

这里踩过一个坑：浏览器会话里会残留上一条视频的请求记录，结果**新视频的条目里写进了上一条的内容**。解决办法是每次先回到空白页清掉噪音，并且在下载后**用页面时长校验**（页面 56.9 秒、文件却 451 秒 → 直接报错重取）。

### 2. 转写：GPU + 合适的参数

faster-whisper large-v3 跑在 CUDA 上，2 分钟的视频约 25 秒出稿。两个参数值得抄：

- `beam_size=1`：比默认 beam=5 快约 35%，中文质量差异很小；
- `condition_on_previous_text=False`：降低长音频复读概率。
- 模型别重复加载：整个转写放在一次进程里跑完。

### 3. 提炼与浏览：让 AI 做它擅长的那一段

脚本只负责「把素材准备好」——逐字稿、正文、元信息、草稿条目。**总结、要点、金句、标签交给 AI**，因为这部分没法用规则替代。

最后把整个知识库打包成**一个单文件网页**：双击就能打开，支持全文搜索、标签筛选、图片预览，不需要任何服务器。

## 四、实测数据

| 环节 | 耗时 |
|---|---|
| 公众号文章：抓正文 + 存图 + 生成条目 + 更新索引 | 3–8 秒 |
| 抖音视频：取流 + 下载 + 合并 | 5–10 秒 |
| 转写（133 秒视频，RTX 2070） | 约 25 秒 |
| 端到端（含生成条目） | 30–40 秒 |

对比「手动看视频做笔记」，省下的主要不是打字时间，而是**你不再需要重看一遍**。

## 五、四个坑（提前避）

1. **旧直链污染**：浏览器会话里的历史请求会被当成新视频，用页面时长校验兜底。
2. **分轨视频**：只下视频轨会得到没声音的 mp4，要单独下音频轨再合并。
3. **公众号「环境异常」**：同一链接换个 User-Agent 往往就能抓到；不行才上浏览器。
4. **编码问题**：PowerShell 5.1 读无 BOM 的 UTF-8 脚本会乱码；中文文件要么带 BOM、要么显式指定编码。

## 六、把它接到 AutoClaw 上（可行性参考）

这套流程是「取数 → 转写 → 提炼 → 入库」四段，每一段都可以换成 AutoClaw 的角色，改动量很小：

| 环节 | 现在的实现 | 接入 AutoClaw 的做法 |
|---|---|---|
| 微信入口 | 微信对话直接发链接 | 用 AutoClaw 接微信，链接进来后触发同一套脚本 |
| 浏览器取流 | `agent-browser` 打开视频页、抓媒体直链 | 换成 AutoClaw / AutoGLM 的浏览器代理执行同样的「打开 → 播放 → 抓直链」动作 |
| 提炼与写稿 | 本地把逐字稿交给模型回填总结 | 交给 AutoClaw 的模型，并让它顺手产出多平台文案 |
| 归档与检索 | Markdown + 单文件浏览页 | 不变，AutoClaw 只负责「抓」和「写」，知识库依然是本地文件 |

换句话说：**AutoClaw 适合承担「浏览器操作 + 内容加工」这两段，本地脚本负责稳定、可重复的取数与落库**。两边通过一个共享目录（或一条命令）衔接即可，不需要把整套流水线都搬进去。

这套组合的价值在于：以后你只要在微信里丢一条链接，剩下的取数、转写、写稿、入库全部自动完成。

## 七、开源与复用

整套流程已经整理成一个 Skill 开源出来，包含取流、转写、公众号抓取、条目模板和浏览页生成：

**github.com/starxxy/knowledge-base-pipeline**（MIT）

只要有 Python + ffmpeg，改一份 `config.json` 就能跑。欢迎拿去接自己的收藏夹、播客，或者任何「有链接、有文字」的内容源。
